# 复盘与下一步

以下是本次 AI 辅助实现过程的工程复盘，不代替候选人个人陈述。

## 最难的问题

难点是区分“看起来引用了文档”和“结论真的受证据约束”。只让模型附上 D01 很容易漏掉 D02，或者只截取支持结论的几个字。因此将约束放在可执行代码里：检索扩展同主题候选、只准引用成功读取的完整文本、未读候选阻止结束、冲突不能被新版本日期掩盖。

另一个难点是没有 API 密钥时如何展示真实动态选择。离线 Mock 可以测工程流程，却不能证明模型判断。本次同时保留原生 API 接入和 stdio 桥，由当前 Codex 会话逐轮观察结果后选动作，并明确写出该验证不是自动 API 端到端测试。这比给规则分支贴上 ReAct 标签更便于评审核验。

## 实际改进

- 首次运行发现数据根路径错误并修复，随后用 CLI 子进程测试覆盖实际入口。
- 检查检索改写时去掉易召回无关产品的通用关键词，避免资料外问题被误答。
- 加入反例测试，拒绝未读引用、部分引用和漏引冲突一方。
- 对工具失败保留实际失败事件和既有成功结果；永久失败不重试到上限才停止。
- API 连续请求保留函数调用 ID 和必要输出上下文；错误脱敏，缺配置不回退 Mock。

## 得到的工程认识

模型应该选择下一步，运行时应约束可执行范围和完成条件。两者有不同职责。严格引用能减少事实编造，却不能单独解决检索相关性、范围判定、语义冲突和答案完整性。

测试需要包含反例和资料变更，而不只是“输出字段存在”。同样，记录必须说明证据来自哪一层：本地单测、Mock 场景、交互模型、自动 API，不能混算成一个成功率。

## 下一步优先级

1. 配置真实 API，至少对正常、冲突、工具失败各运行数次，保留全部失败和 token/耗时记录；使用新资料做盲测。
2. 建立明确的制度适用范围和有效期数据模型。只有权威覆盖关系明确时才允许解决冲突。
3. 增加检索相关性评估、更多中文改写样本和长文片段引用，再考虑向量检索。
4. 需要真实员工使用时再增加身份权限、外部文档接入、限流和状态持久化。
