# 需求与成功标准

## 用户和问题

员工询问制度或产品功能，希望知道答案来自哪里、适用于哪个版本，以及现有资料能否给出确定结论。最危险的失败是引用不支持答案，或在冲突资料中擅自挑选一个结论。

选择题目 3：企业知识问答 Agent。范围为单次 CLI 任务，可携带最多 20 条历史消息。交付不涉及真实企业数据、线上部署或前端。

## 输入与输出

输入为 `question` 和可选 `history`；测试时可加 `failures` 控制工具故障。文档包含唯一 ID、标题、版本日期、主题键、适用范围、优先级、检索关键词、完整原文。

输出包含任务状态、回答、引用 ID/版本日期/原文、资料缺口，以及公开执行记录。资料不足不等于“政策不存在”；工具错误不等于“没有相关资料”。

| 状态 | 含义 |
|---|---|
| answered | 根据实际读取且通过校验的原文回答 |
| conflict | 现有资料有不同规定，无充分依据确定唯一规则 |
| needs_clarification | 用户缺少必要输入，需补充问题或范围 |
| insufficient_evidence | 已查资料不能支持回答 |
| incomplete | 工具/模型错误或预算上限导致任务未完成 |

## 必须验收

| 验收点 | 可观察成功标准 | 示例输入 |
|---|---|---|
| 明确答案 | 返回支持字幕编辑的完整 P01 原文和版本 | clear_answer.json |
| 文档冲突 | 读 D01/D02，补查后仍冲突则同时引用，不按日期选答案 | conflict.json |
| 资料外问题 | 查询无结果后补查或停止，明确资料缺口，不凭常识作答 | outside.json |
| 改写相似问题 | “自动配字”可以检索到字幕资料 | paraphrase.json |
| 上下文追问 | “那它可以修改吗”结合上文重新检索，不将历史答案当证据 | context.json |
| 工具失败 | 临时故障可由模型选择重试；永久故障返回 incomplete | failure_once / failure_permanent.json |

另测缺少问题、执行上限、伪造引用、未读引用、漏读冲突文档，以及替换资料后答案和动作改变。成功不以“所有任务都 answered”为目标；正确暴露冲突、缺资料和失败也是符合业务要求的结果。

## 非目标与边界

- 语料仅 5 份合成文档，关键词/同义词检索，不承诺开放领域语义召回率。
- 无文档权限系统、增量索引、跨进程恢复、流式 API、生产限流和自动 API 重试。
- 引用完整短段落，优先可核验性；当前不做长文摘要或复杂问句的自然语言综合。
- 当前已提供本地与交互式模型验证，并整理为 GitHub 提交；真实 API 自动运行仍待配置。
